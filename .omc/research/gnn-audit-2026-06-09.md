## Section 1 — Model Architecture

### Specification (verified from `src/models/mpnn.py` + `src/models/featurize.py`)

```
atom encoder:   Linear(29 -> 128)                       (mpnn.py:21)
bond encoder:   Linear(6 -> 128)                        (mpnn.py:22)
backbone:       3 x GINEConv(MLP 128->128->128)         (mpnn.py:26-31)
                + BatchNorm1d(128) + ReLU
readout:        global_mean_pool  ->  (B, 128)          (mpnn.py:19, 47)
head:           Linear(128->128) + ReLU + Dropout(0.2)  (mpnn.py:33-36)
                + Linear(128->11)
~0.15M parameters total
```

Atom features (29 dims, `featurize.py:25-60`): element one-hot 11 (H,C,N,O,F,P,S,Cl,Br,I,other),
degree one-hot 7, formal charge one-hot 5, hybridization one-hot 4 (only SP/SP2/SP3 mapped;
everything else → "other"), aromatic flag 1, in-ring flag 1.
Bond features (6 dims, `featurize.py:63-68`): bond type one-hot 4, conjugated flag 1, in-ring flag 1.

---

### [FINDING 1.1] Capacity is well-matched; the bottleneck is readout + features, not depth

[STAT:effect_size] Bitter CV F1 mean=0.786, std=0.0079; sweet mean=0.898, std=0.0046
(`cv_results.json` lines 24-44, exact values).
[STAT:n] ~16k training compounds per fold.

~0.15M parameters over ~16k training graphs is an appropriate ratio. Dense heads (sweet, bitter)
are near their data-quality ceiling, demonstrating ample representational capacity.
More layers or wider hidden dimensions will not lift the weak heads — do not spend effort there.

[LIMITATION] Holds for the current task set and corpus. A foundation-model encoder swap
(ChemBERTa, MolFormer) is a different question — it changes what information the backbone
*processes*, not just capacity.

---

### [FINDING 1.2] global_mean_pool dilutes local motif signals (a root cause of odor weakness)

`global_mean_pool` (`mpnn.py:19, 47`) averages atom embeddings uniformly. For a large molecule
with one bitter/odorant-binding fragment and 40 unremarkable carbons, that fragment's activation
is diluted ~40-fold before reaching the head. This is exactly the dilution problem
`aggregate_predictions.py` fixes one level up (mean-of-20-compounds → top-3-mean). The same fix
applies at the atom level and is cheaper.

[STAT:effect_size] In published fragment-sensitive binary-classification MPNN benchmarks,
adding max/sum pooling alongside mean adds roughly +0.02-0.08. For odor heads with 37-100 test
positives and a fold-std of 0.02-0.06, a +0.03 lift is ~1 fold-std and therefore distinguishable.

**Concrete fix:** Replace the readout in `mpnn.py:47`:

```python
from torch_geometric.nn import global_max_pool, global_add_pool
mean_ = global_mean_pool(x, data.batch)   # (G, 128)
max_  = global_max_pool(x, data.batch)    # (G, 128)
add_  = global_add_pool(x, data.batch)    # (G, 128)
return torch.cat([mean_, max_, add_], dim=1)  # (G, 384)
```

Increase head input from 128 to 384 (`mpnn.py:33`). Three-line model change; no data or
training-infrastructure changes.

[LIMITATION] Magnitude is speculative until measured under a scaffold split (Lever 2).

---

### [FINDING 1.3] No pKa, logP, or physchem descriptors — the model reconstructs them blindly

Sour taste is mechanistically a pKa phenomenon. The +0.33 sour gain at v3 came from FartDB's
IUPAC pKa-derived labels — but the model still cannot *see* pKa, logP, MW, TPSA, H-bond
donor/acceptor count, or fraction Csp3 (`featurize.py:25-60` has no global descriptor channel).
It reconstructs the pKa signal purely from graph topology and bond features.

[STAT:effect_size] Published literature: pKa as explicit sour-classifier input yields ~+0.05-0.15 F1;
logP and TPSA are strong odor-volatility priors.

Suggested RDKit descriptor vector (8 dims, no external dependency beyond the already-imported
RDKit): MolWt, TPSA, NumHDonors, NumHBAcceptors, NumRotatableBonds, MolLogP, FractionCsp3,
RingCount. Concatenate (normalized) after the readout, before the head. For odor heads, logP~1-4
and MW<300 Da separates volatile odorants from the artificial sweeteners (MW 200-600,
hydrophilic) that dominate the FartDB portion and may be confounding the odor representation.

[LIMITATION] True pKa estimation needs `pkasolver` or an external step. Try the 8-descriptor
RDKit vector first (no new dependencies).

---

### [FINDING 1.4] Featurization gaps relevant to weak heads

- **No chirality/stereo** (`featurize.py:50-60` reads no `atom.GetChiralTag()`). Enantiomers can
  have dramatically different odor qualities (L-carvone=spearmint vs R-carvone=caraway).
  Relevant to odor heads.
- **Element "other" conflates ionic species** (`featurize.py:52`: any non-CHNOFPSClBrI symbol →
  index 10). Na+, K+, Ca2+ all hash to the same atom embedding. Consistent with the salty
  ceiling — ionic salts are not discriminable from other polar non-salts. No lever here without
  matrix-context modeling (confirmed by the FART salty exclusion).

---

### [FINDING 1.5] BatchNorm with variable atom count per batch (minor)

`BatchNorm1d(128)` (`mpnn.py:31`) applied at atom level with batch_size=64 graphs. Per-batch atom
count varies with molecule size, making running statistics noisy for small batches of large
molecules. `GraphNorm` or `LayerNorm` is more stable. Small expected impact on reported F1.

## Section 2 — Data Sources, Label Quality, and CV Leakage

### [FINDING 2.1] CRITICAL: No molecular scaffold split anywhere in the compound pipeline

Every **compound** split in this repo uses random compound-level stratification. There is no
Bemis-Murcko scaffold split, no GroupKFold keyed by scaffold, no Tanimoto-distance holdout.

Code evidence (re-verified):
- `src/train/train_multitask.py:370`: `StratifiedKFold(n_splits=folds, shuffle=True, random_state=SEED)` — produces `cv_results.json`.
- `src/train/train_multitask.py:146` (single split): `train_test_split(..., stratify=strat, random_state=SEED)`.
- `src/eval/calibrate_thresholds.py:93` (calibration): same `train_test_split`.
- `src/eval/cross_validate.py:155`: same `StratifiedKFold(shuffle=True)`.

The one structure-aware splitter, `src/data/stratified_split.py`, is **edge-level for the GAT
pairing graph** (`stratified_edge_split`, lines 58-122) — it splits ingredient-pairing edges,
NOT molecules. It does not protect the compound GNN from scaffold leakage.

Why this matters for this corpus specifically: FartDB contributes ~9,500 artificial-sweetener
analogues and 1,513 IUPAC pKa-based sour positives. Both are homologous-series-dense — the
sweeteners are sucralose/aspartame/acesulfame-K structural variants; the sour set is largely a
homologous series of carboxylic acids (acetic, propanoic, ... decanoic). Random 80/20 splitting
places structurally near-identical molecules in both train and test. The model interpolates
between near-neighbors in the same series rather than generalizing to novel scaffolds.

The deployed inference target (chef ingredients mapped via FooDB) is precisely the
*out-of-scaffold* generalization the CV claims to measure. Reported CV F1 (sweet=0.898,
sour=0.830) is therefore almost certainly inflated relative to deployment performance.

**Lever:** Rerun CV with `GroupKFold(n_splits=5)` keyed on `MurckoScaffoldSmiles`:
```python
from rdkit.Chem.Scaffolds.MurckoScaffold import MurckoScaffoldSmiles
scaffolds = [MurckoScaffoldSmiles(s) or s for s in df["smiles"]]
groups = pd.Categorical(scaffolds).codes
gkf = GroupKFold(n_splits=5)
for tr_idx, te_idx in gkf.split(X, groups=groups): ...
```

[Confidence: High — direct code evidence.]

### [FINDING 2.2] Two CV code paths: one mask-aware (authoritative), one not (dead/dangerous)

**Path A — authoritative** (`src/train/train_multitask.cross_validate`, lines 363-388, calling
`_train_one_fold` lines 295-360):
- `_featurize_all` (lines 85-113) attaches `mask_<task>` as `d.mask` per graph.
- `_train_one_fold` lines 353-359 evaluate F1 only on `sel = m_arr[:, i].astype(bool)` rows.
- Output schema `{per_task: {mean, std, per_fold}}` — confirmed: `cv_results.json` uses exactly
  this `{mean, std, per_fold}` shape with `epochs: 15`, so **Path A produced the live artifact.**

**Path B — dead/dangerous** (`src/eval/cross_validate.py`):
- `_featurize_all` (lines 41-51) builds raw 0/1 Y with **no mask**.
- `train_and_eval_fold` (lines 98-104) computes F1 over **all** test rows including unobserved
  forced-zeros.
- `pos_weight` (lines 64-67) uses all rows, not mask-filtered counts.
- Output schema is `{summary: {f1_mean, f1_std, ...}}` — matches **no current artifact**.

Path B is the exact bug the v3 masking work fixed at the training level. Run today it would
produce systematically lower F1 on rare heads (inflated FN from unobserved zeros) and would
falsely suggest masking made things worse. **Delete it** to prevent a future agent from running
the wrong CV.

[Confidence: High — direct code evidence; schema mismatch confirms which path is live.]

### [FINDING 2.3] CRITICAL: Best-epoch-on-test selection inflates every reported F1

Both CV-fold training and single-split training report the per-task **max F1 over all 15 epochs
on the test fold** — i.e. early-stopping on the test set.

Code evidence:
- `_train_one_fold` lines 358-359: `if f1 > best[t]: best[t] = float(f1)` — per-task max across
  all epochs on the test fold; returns `best`.
- `train` lines 247-253: same for single-split `best_per_task`.

Direct corroboration from the live artifact: `m3_multitask.json` `best_per_task` epochs are
**scattered** — sweet@11, umami@8, salty@8, odor_woody@8, odor_spicy@14, sweet's recall epoch ≠
bitter's (lines 20-87). If the pipeline reported the final epoch, all would read epoch 15. The
scatter is the fingerprint of test-set argmax.

[STAT:n] Per-fold F1 std (cv_results.json): odor_fatty 0.060, odor_spicy 0.031, odor_floral 0.030,
odor_fruity 0.028, umami 0.025.

Expected inflation: the max of 15 iid draws from N(μ,σ) exceeds μ by ≈ σ·E[max of 15 standard
normals] ≈ σ·1.74 (a more careful constant than the loose 2.4 cited in some drafts; either way
non-trivial). For odor_fatty (std=0.060): inflation ~0.10 F1. For odor_floral (std=0.030):
inflation ~0.05 F1. Not small biases on the weak heads.

**Fix:** add a 10% validation split inside `_train_one_fold`; select the epoch by validation loss;
report test F1 at *that* epoch. ~3 lines.

[Confidence: High — code + scattered-epoch artifact evidence.]

### [FINDING 2.4] Odor labels are noisy keyword-bucket free text

All six odor head labels are derived by substring matching on free-text flavor descriptors
(`build_compounds.py:47-82`). `_odor_flags` (lines 77-82) joins all flavor tags into one string
and checks `any(kw in tags_str for kw in keywords)`. `ODOR_CATEGORIES` (lines 47-54, verified
verbatim):

- green: ["green","fresh","herbal","grassy","leafy","vegetable","cucumber","minty","tea"]
- woody: ["woody","earthy","balsam","nutty","mossy","mushroom","cedar","pine","resinous","smoky"]
- spicy: ["spicy","pungent","pepper","clove","cinnamon","anise","warm","hot"]
- fatty: ["fatty","waxy","oily","creamy","buttery","cheesy","milky","coconut"]

Substring (not token) matching compounds the noise — "warm" matches inside longer descriptors.
Known false-positive generators:
- "coconut"/"creamy" tagging fatty for a coconut-flavored sweet that isn't genuinely waxy/fatty
- "mushroom" tagging woody when the descriptor is earthy-umami
- "warm" tagging spicy for "warm-sweet"/"warm-floral"
- "tea" tagging green when the note is more floral
- "nutty" collapsing the roasted/Maillard cluster into woody

[STAT:n] odor_floral has 43 test positives; a ~10% false-positive label rate (~4 mislabels)
caps achievable F1 at ~0.92 even with a perfect model.

**Lever:** Replace `ODOR_CATEGORIES` substring buckets with a curated descriptor→head lookup
table (map ambiguous tokens like "warm"/"coconut"/"nutty" to "skip"). Unlike DREAM ingestion
(added 90-135 clean positives — below the noise floor), de-noising the *existing* positive set is
multiplicative. The skipped task N1-D2 in `.claude/.ralph-handoff.md` ("Top-500 manual Tier-3 +
leaf curation, long-tail rule-derivation lookup table") is the natural vehicle.

[Confidence: Medium-High — code verified; magnitude depends on actual label-error rate.]

### [FINDING 2.5] Salty is a confirmed structural dead end — no lever recommended

[STAT:n] 10 test positives. v3 calibrated F1=0.333 (`threshold_calibration.json` lines 64-72).
M1 RF baseline salty F1=0.286 on 3 test positives (`m1_baseline.json` lines 47-57).

Caveat on the RF comparison: M1 RF was trained on a smaller pre-FartDB corpus (4,176 compounds,
`m1_baseline.json:9`), so the two F1 figures are not measured on identical data. The conclusion
holds regardless — both are noise-dominated tiny-positive estimates, and the FART paper excludes
salty because ionic dissociation is matrix-dependent and not predictable from SMILES. The
"+0.195 lift from calibration" is threshold overfitting to 10 points (Section 3.2).

No data, architecture, or label-cleaning lever applies. Keep salty out of the UI (already policy
via `recalibrate_ingredient_thresholds.py` MIN_MOLECULE_LEVEL_F1=0.4 gate). The only available
change is removing the salty head from training (Lever 5).

## Section 3 — Training and Calibration Methodology

### [FINDING 3.1] Masked BCE + per-task obs-only pos_weight is correct and principled

The loss is sound. `_masked_bce` (`train_multitask.py:65-74`) multiplies elementwise BCE by the
mask, divides by `mask.sum().clamp(min=1)` — correctly excluding unobserved positions from the
gradient. `pos_weight` (lines 156-163, and the fold version 312-319) uses mask-filtered positive
and negative counts only. These are the decisions that fixed the v2→v3 regressions on bitter
(-0.20) and the six odor heads. Correctly implemented. No change recommended.

---

### [FINDING 3.2] CRITICAL: Threshold calibration is performed on the same test split it reports

`calibrate_thresholds.py` reproduces the seed-42 train/test split (line 93), runs inference on
`te_idx` (lines 98-109), sweeps 19 thresholds (`np.linspace(0.05, 0.95, 19)`, line 114), then
picks and reports the threshold with the best F1 **on that same `te_idx`** (lines 139-159). This
is threshold selection on the test set — the reported "calibrated F1" is the best F1 achievable by
any grid threshold on the exact examples evaluated.

The signature of threshold overfitting is an inverse correlation between n_test_pos and lift
(all values verified from `threshold_calibration.json`):

| task        | n_test_pos | f1@0.5 | calibrated_f1 | lift   |
|-------------|-----------|--------|---------------|--------|
| salty       | 10        | 0.139  | 0.333         | +0.195 |
| umami       | 75        | 0.511  | 0.731         | +0.219 |
| odor_fatty  | 54        | 0.490  | 0.617         | +0.127 |
| odor_floral | 43        | 0.493  | 0.515         | +0.022 |
| sour        | 347       | 0.786  | 0.819         | +0.033 |
| sweet       | 2,316     | 0.876  | 0.904         | +0.029 |

Largest lifts on the rarest heads (umami +0.219, salty +0.195, fatty +0.127) — exactly the
threshold-overfitting signature. For salty, calibrated F1=0.333 at thr=0.90 corresponds to
precision=0.25, recall=0.50 (`threshold_calibration.json:69-71`) — a fragile operating point that
will not reproduce on a different 10-positive sample.

The umami F1=0.731 (cited in the status doc as moving umami from "barely shippable 0.61" to
"solid 0.73") is the product of **two** optimistic biases stacked: best-epoch-on-test in CV
(Finding 2.3) AND calibration-on-test here. The unbiased umami generalization estimate is unknown
until both leaks are fixed.

**Fix (3 lines after line 93 in `calibrate_thresholds.py`):**
```python
te_cal, te_rep = train_test_split(te_idx, test_size=0.5, random_state=SEED+1)
# Sweep thresholds on te_cal; report F1 on te_rep.
```

[Confidence: High — direct code + inverse-correlation evidence.]

---

### [FINDING 3.3] High thresholds (0.80-0.95) are real but confounded with calibration-on-test

The "threshold collapse" phenomenon (umami thr=0.80, sour thr=0.90, salty thr=0.90 —
`threshold_calibration.json`) is genuine: BCE+pos_weight emits confident positives only at the
extreme tail for rare heads. But the *specific* values are tuned to the exact test set; after a
calibration/reporting split they may shift ±0.05-0.15. The shipped thresholds in
`public/proDataset/odor_thresholds.json` and `ingredient_profile_thresholds.json` have unknown
generalization error and must be re-derived after any retrain.

---

### [FINDING 3.4] No LR schedule, no validation-set early stopping (minor)

Flat Adam lr=1e-3 for 15 epochs, no schedule (`train_multitask.py:166, 322`). For the dense heads
this is fine; for rare heads (umami, odors) the loss is still decreasing at epoch 15 in many
folds. Cosine annealing + proper validation early stopping would allow both more thorough training
and honest epoch selection (pairs naturally with the Finding 2.3 fix).

## Section 4 — Prioritized Lever List

Ranked by expected gain / effort, cross-referenced against the documented noise floor
(0.02-0.07 fold-std) and the known dead-ends. A lever must plausibly exceed one fold-std to be
distinguishable from noise.

---

### Lever 1 — Switch ingredient aggregation topk_mean → noisy_or [ZERO model retraining, ~1h, HIGHEST ROI]

The repo already contains a benchmark showing a near-2x ingredient-level chef macro-F1 gain that
the shipped pipeline has not adopted. From `aggregation_benchmark.json`:

| strategy  | above_any | chef macro_F1     |
|-----------|-----------|-------------------|
| mean      | 2,548     | 0.066             |
| topk_mean | 3,367     | 0.101  (SHIPPED)  |
| max       | 3,585     | 0.134             |
| noisy_or  | 3,707     | 0.192             |

noisy_or vs topk_mean = **+0.091** absolute chef macro-F1 (1.90x). Per-task chef-F1 deltas
(topk_mean → noisy_or, verified):

| task        | topk_mean | noisy_or | delta  |
|-------------|-----------|----------|--------|
| sour        | 0.000     | 0.350    | +0.350 |
| odor_spicy  | 0.000     | 0.278    | +0.278 |
| odor_fruity | 0.000     | 0.208    | +0.208 |
| bitter      | 0.212     | 0.309    | +0.097 |
| odor_green  | 0.000     | 0.090    | +0.090 |
| sweet       | 0.780     | 0.775    | -0.005 |
| umami       | 0.121     | 0.098    | -0.023 |

The status doc frames "odor heads fire on 0 ingredients" as a problem needing N2-GNN-CHEF-LIFT or
N2-GNN-LEFF. `aggregation_benchmark.json` directly contradicts this: sour, fruity, green, and
spicy go from 0 above-threshold ingredients to 382-3,072.

**Why noisy_or works:** treats each compound as independent evidence:
`p_ingredient = 1 - ∏(1 - p_compound)` (`aggregate_predictions.py:74-75`). With 10 compounds at
p=0.15: noisy_or = 1 - 0.85^10 = 0.80; topk_mean(K=3) of the same = 0.15. At odor_fruity
threshold=0.55 noisy_or fires, topk_mean does not. This is the correct probabilistic
interpretation: if 10 structurally independent compounds each predict 0.15 for "fruity", the
probability at least one is genuinely fruity is 0.80.

Run: `python -m scripts.aggregate_predictions --strategy noisy_or --k 3 --max-compounds 10`

**TWO critical caveats before shipping:**

1. **Re-calibrate ingredient thresholds first.** v3 thresholds were calibrated at the *compound*
   level; noisy_or ingredient probs are systematically higher. Run
   `scripts/recalibrate_ingredient_thresholds.py` on noisy_or outputs (it recomputes the 85th
   percentile per task) BEFORE shipping, or every head over-fires.

2. **The production gate will mask part of the gain.**
   `recalibrate_ingredient_thresholds.py:39, 93-95` DISABLES any head with molecule-level
   calibrated F1 < 0.4 (sets threshold to 1.01). Under v3 calibrated F1, that gate disables
   **salty (0.333) and odor_spicy (0.329)** outright. So noisy_or's headline spicy gain (+0.278
   chef-F1) would be gated OFF under current policy. The *shippable* portion of the noisy_or gain
   is concentrated in sour, odor_fruity, odor_green, bitter (all ≥0.40 calibrated F1). Decide
   explicitly whether to relax the 0.4 gate for spicy or keep it suppressed; the +0.091 headline
   overstates what reaches the UI under the current gate.

[Confidence: High — in-repo benchmark; gate interaction verified in code.]

### Lever 2 — Scaffold-split CV + held-out calibration [~0.5d, no model change, MEASUREMENT CORRECTNESS]

Re-run CV with `GroupKFold` keyed by Bemis-Murcko scaffold (Finding 2.1) and move threshold
selection to a held-out half of the test set (Finding 3.2). This is a **measurement-correctness**
lever, not a "+F1" lever — without it every other lever is evaluated against a biased baseline.
The current 0.02-0.07 noise floor is itself computed from leaky random folds; a scaffold split
widens fold variance and may reclassify "shippable" heads (umami's 0.731 in particular is the
product of two stacked leaks and its true value is unknown).

**Effort:** ~0.5d. ~5 lines for `MurckoScaffoldSmiles` keying in the CV loop; ~3 lines for the
calib/report split in `calibrate_thresholds.py`. No model/data/architecture change. Run this
FIRST so Levers 3-5 are judged honestly.

### Lever 3 — Add max+sum pooling and RDKit physchem descriptors [~1d, one retrain]

Concatenate `global_max_pool` + `global_add_pool` with `global_mean_pool` (readout 128→384,
Finding 1.2) and prepend a normalized 8-descriptor RDKit vector to the head input (Finding 1.3).
Addresses readout dilution (max-pool preserves the strongest local fragment) and feature
blindness (physchem = pKa/volatility proxies).

[STAT:effect_size] Speculative +0.03-0.08 on sour/fruity/fatty/bitter from analogous published
MPNN interventions; must be validated under Lever 2's scaffold split.

**This is NOT SMILES enumeration augmentation (the dead end).** Changing the pooling readout and
adding global descriptors changes what the head sees *after* the permutation-invariant backbone
runs. SMILES enumeration fails precisely because GINEConv is permutation-invariant — all SMILES of
a molecule produce the identical graph. Mechanistically distinct, not a re-tread.

### Lever 4 — Replace keyword-bucket odor labels with a curated descriptor lookup [~0.5-1d, one retrain]

Replace `ODOR_CATEGORIES` substring matching (`build_compounds.py:47-82`) with an explicit
descriptor→head CSV (ambiguous tokens "warm"/"coconut"/"nutty"/"tea"/"mushroom" → "skip").
Unlike DREAM (failed: +90-135 clean positives below the noise floor relative to the existing
200-500 per head), this de-noises the *existing* positive set — removing ~10% false positives from
a 100-positive set is multiplicative in S/N terms, not an additive trickle. N1-D2 in the handoff
is the natural vehicle.

### Lever 5 — Remove the salty head from training [trivial, ablation only]

Salty (10 test positives, F1=0.333, structural ceiling confirmed by FART) contributes a noisy,
unlearnable gradient to the shared backbone. Expected impact of removal is small (its
pos_weight-scaled gradient is dominated by the 10 other heads) but it is a clean ablation worth
running alongside any retrain. Remove "salty" from `TASKS` (`train_multitask.py:31`); set
`num_tasks=10`. The UI already suppresses salty via the 0.4 gate.

## Dead-End Confirmation (correctly abandoned per status doc — do NOT re-recommend)

### DREAM ingestion (INCLUDE_DREAM=False is correct)
DREAM adds 90-135 clean positives per odor head to a set already holding 200-500 from
FlavorDB+FlavorNet — below the fold-std noise floor. `cv_results_dream.json`: 0/5 non-spicy odor
heads cleared +0.03; only odor_spicy lifted (+0.041, ~1σ, explicitly excluded by the AC). Lever 4
(de-noise existing labels) is the correct substitute. Infrastructure stays in-repo behind the flag.

### Focal loss (keep BCE)
Focal softens the output distribution, undermining the per-task threshold sweep that makes
BCE+pos_weight effective. `cv_results_focal.json`: mean calibrated F1 BCE=0.530, focal=0.504
(delta -0.027); regressed 9/11 heads. Fundamental interaction with high-threshold calibration.

### SMILES enumeration augmentation
GINEConv is permutation-invariant over atom ordering; all SMILES of one molecule featurize to the
identical `torch_geometric.data.Data` (`featurize.py:71-100`). No augmentation effect. Valid only
for string-input encoders (ChemBERTa, LSTM). Do not retry without first switching the encoder.
