# share as-built specs

## SHARE-1 — Public recipe page and /r/ links for the app's built-in recipes

New route /r/<kind>/<slug> (kind cocktail, sauce or dish) rendering SharedRecipePage.jsx: name, ingredients with amounts, method, glass or vessel, and the flavor profile chart with its 'visual guide' label. Pure resolver src/data/sharedRecipe.js: parseSharePath(pathname), slugFor(kind, item), resolveBuiltIn(kind, slug) over cocktailCodexV2.js, sauceCodex.js and the Cookbook dishes, returning one normalised shape { kind, name, lines, method, glass, category } that SHARE-6 reuses for user copies. The page opens without the landing picker, without sign-in and without loading the full pairing dataset. Unknown slug shows 'This recipe is no longer shared' with a button to the starting page.

## SHARE-2 — Share button and share sheet on recipe cards

ShareSheet.jsx plus a Share button on built-in and own cocktail, sauce and Cookbook dish cards and on the result step of the three invent panels after saving. Phone: navigator.share with title, text and url. Elsewhere: Copy link, X, Facebook, Pinterest and WhatsApp as plain share URLs (pure builder src/data/shareTargets.js, no third-party scripts), and a Download image slot that SHARE-5 fills. For built-in recipes the link is the /r/<kind>/<slug> link from SHARE-1. For a user's own recipe the button is present but routes to the publish step that SHARE-6 adds; until then it is hidden behind one flag so this task can ship alone.

## SHARE-3 — Save to my cookbook and Make it your own from a shared page, with the sign-up prompt

On SharedRecipePage: 'Save to my cookbook' (or 'my cocktails' / 'my sauces'), 'Make it your own', and for signed-out visitors a one-line invitation with 'Create a free account'. Save reuses useSaveInvention and InventSaveOverlay; the overlay copy says why an account is needed; the save completes after sign-in returns, including the redirect sign-in flow (the pending save survives the reload). The saved copy carries sharedFrom (slug or share id). Make it your own opens that lab's invent panel through its seed prop with the recipe's lines and category. The invitation is inline, shown once per page, never a blocking pop-up.

## SHARE-4 — Link preview: a function that fills in the title, description and image for /r/ links

Cloud Function sharePreview (functions/src/share/) and a hosting rewrite /r/** to it, placed before the catch-all. It returns the built app's index.html with <title>, og:title, og:description (the first ingredients), og:image, og:url, og:type and twitter:card=summary_large_image filled in for the recipe; every value HTML-escaped. Built-in recipes resolve from a small JSON index generated at build time (scripts/buildShareIndex.mjs) so the function does not bundle the app's data modules. Unknown or removed ids get the generic site tags. Cache-Control: public, max-age=600. If anything throws, it serves the unmodified index.html. Also adds generic og tags to index.html for every other page.

## SHARE-5 — The recipe card images: server-drawn for previews; a downloadable set for Instagram and TikTok

One pure layout description src/data/shareCardLayout.js (name, ingredient lines, the 11-axis flavor chart as plain numbers, method, the short link as printed text, site name, chalkboard palette) consumed by two renderers. Server: Cloud Function shareCard behind a hosting rewrite /r-img/**, drawing a 1200x630 PNG with satori and resvg and bundled fonts, Cache-Control one day. Browser (canvas), behind the share sheet: (a) a portrait card 1080x1350 for the Instagram feed; (b) a tall card 1080x1920 for Stories and TikTok, with the top and bottom 250px kept clear of text because both apps cover them; (c) a swipeable set of three cards in either size: 1 name and flavor chart, 2 ingredients, 3 method. Every card prints the short link (for example neuralflavor.web.app/r/ab12cd) since neither app allows a tappable link in a post. Share sheet additions: 'Share images' hands the PNG files to navigator.share where navigator.canShare({ files }) is true, so the person picks Instagram or TikTok in the phone's own menu; 'Download images' everywhere else; 'Copy caption' copies a ready caption (recipe name, the link as text, two hashtags) because the share menu does not carry text with files; one line says the link was copied for an Instagram Story link sticker. Long names shrink, then wrap to two lines, then truncate; long ingredient lists and methods continue with '+N more at the link'. The chart is labelled 'flavor chart: a visual guide'. No posting API of Instagram or TikTok is used. A short video is NOT part of this task (later experiment, needs testing on real phones).

## SHARE-6 — Share a recipe the user made: publish a frozen copy, choose the name shown, unshare

New public collection shared/{id} (shape and limits in the spec) and firestore.rules for it: get by id for anyone, no list, create only signed in as owner within the limits, owner may set removed or delete, nothing else. src/data/sharePublish.js (pure toSharedDoc with the limits, and the Firestore calls). The share sheet's publish step for own items: shows exactly what will be public, the name choice (first name / typed nickname / nothing, default nothing), then 'Create link'. profiles/{uid}.shares tracks links (cap 50 live); an unedited item reuses its link. Profile gains 'Shared links' with Unshare. /r/<id> renders through SharedRecipePage and the preview and card functions read shared/{id}; removed or missing shows 'no longer shared' and generic preview tags. Must ship together with SHARE-7.

## SHARE-7 — Report, takedown, docs and the final pass

A 'Report' link on pages for user-shared recipes: reason picker and optional note written to shareReports/{auto} (rules: create by anyone within size limits, no read, no update), limited to 3 per browser per day. docs/sharing.md: how links work, what is public, how the owner removes a share in the Firebase console (set removed: true), how to read reports, and the three open decisions with their defaults. CLOSEOUT.md (unreleased entry), README.md (including what is and is not recorded about visitors) and BACKLOG.md updated. Final pass in the browser at 375px: share a built-in recipe; publish, open signed out, save through sign-in, unshare; report. Preview checked with a real preview checker only after deploy; until then say so.

## SHARE-8 — Hide flavor charts on shared pages and share cards until the charts are rebuilt

Owner, 2026-11-15: 'Deploy, charts hidden'. After FLAVOR-2, 186 of 599 built-in recipes still draw a chart and on the test set most of those lead with a wrong taste. One exported switch SHARE_CHARTS_ENABLED = false (beside SHARE_OWN_ENABLED) turns the flavor chart off on every PUBLIC share surface: the shared recipe page (no chart section and no 'not enough data' line), the browser share cards (single and set of three; card 1 of the set shows name and details without the chart), the server cards (share-cards.json regenerated with no bars), and the bars stored when a user publishes their own recipe (bars: []). Charts inside the app (Recipe Notebook, invent panels) are unchanged. FLAVOR-6 turns the switch back on.
