# shop as-built specs

## SHOP-1 — Shopping list logic: one line per ingredient, quantities added only when both are specific

src/data/shoppingList.js, pure: List = { items, recipes }, Item = { id, key, label, parts: [{ qty, unit }], checked, from: [recipeId], swappedFrom?, note? }. Functions: emptyList, addLine(list, { key|text, amount }), addRecipe(list, recipe, has, { includeBasics }) returning { list, summary: { added, merged, skippedHave, skippedBasics } }, toggle, remove, clearChecked, replaceItem (for an alternative, keeping swappedFrom so it can be undone), groupByAisle (produce, dairy, meat and fish, dry goods, spices, drinks, other, from the curated ingredient category, with a stated mapping), toText (the existing 'Copy shopping list' format), unchecked count. Matching is by canonical ingredient name through the curation aliases; a checked-off line does not count as on the list. THE MERGE RULE (owner's criterion, spec Decision 3): existing line without a quantity + anything = one line, still without a quantity; existing with a quantity + incoming without = unchanged; both with quantities in like units (both weights, both volumes, or the same count word) = summed, shown in a sensible unit; both with quantities in unlike units = one line with both parts ('2 cloves + 1 tbsp'), never converted by guesswork. 'has' is one predicate over everything the cook has (My kitchen, the sauce pantry, My bar). Kitchen basics (isBasic) are skipped unless includeBasics. Adding a recipe already in list.recipes is reported so the screen can ask first. Reuse parseAmountText, whatDoINeed.js and the alias resolver; do not write a second amount parser.

## SHOP-2 — The shopping list screen: check off as you shop, kept on the device and with the account

ShoppingList.jsx, opened from a new 'Shopping list' entry in the Labs menu that shows the unchecked count. Rows grouped by aisle; each row a large checkbox, the name, the quantity, and which recipes it is for; checking strikes it and drops it to the bottom of its group; rows of at least 44 px, usable one-handed at 375 px. 'Add an item' (typeahead over curated ingredients, free text allowed, optional amount). 'Copy list', 'Clear checked', 'Put checked items in my kitchen' (a button, never automatic; bar items go to My bar), 'Clear all' (asks first), an empty state that explains the two ways to fill it. Storage: localStorage first under one versioned key so it works signed out and offline; when signed in, a `shopping` field on the profile document, merged by item id with last-change-wins per item (each item carries an updatedAt), through the existing useUserProfile sync. State how the known issue recorded in BACKLOG (useUserProfile cloud sync dropping a field) is avoided for this field. The profile rules must allow the new field within a size cap; rules tests on the emulator only.

## SHOP-3 — Add from a recipe: search inside the list, add only what the cook lacks; 'Add to shopping list' on What do I need

In the shopping list, 'Add from a recipe' opens one search box over the built-in cocktails, sauces and dishes and the cook's own saved cocktails, sauces and recipes (by name; reuse the labs' existing search helpers). Picking a recipe shows its lines split into 'You need' (ticked) and 'You have' (unticked, greyed; from My kitchen, the sauce pantry and My bar), with an 'include basics' tick, and 'Add N to the list'. After adding, a short summary says what was added and what merged into lines already there ('garlic: now 5 cloves'). Adding a recipe that is already on the list asks first. The three 'What do I need?' panels (Cocktail Lab, Sauce Lab, Cookbook) gain 'Add to shopping list' beside 'Copy shopping list', using the same addRecipe, with 'Open list' afterwards. The recipe search must not load the large pairing dataset if the list is opened first (state what is fetched).

## SHOP-4 — 'Store doesn't have it?': an alternative for any item on the list

Each unchecked row has 'Store doesn't have it?'. It opens up to three alternatives for that ingredient, each with how to use it (swapUseText, e.g. 'use three quarters as much'), ones the cook already has marked 'you have this'. Sources, in order: kitchenSwaps.js (swapsFor / findSwap) for food, cocktailRiff.swapCandidates for bar items, then same-category neighbours from the curated ingredients ONLY where a stated rule makes that safe (say what the rule is; if none is safe, do not use this source). An alternative that is already on the list merges by the SHOP-1 rule instead of creating a second line. Picking one replaces the row, keeps 'instead of <original>' on it, and offers Undo; if the cook already has the alternative, offer 'Use what I have' which simply removes the row. Where nothing is known the sheet says so plainly and suggests leaving it out only when the recipe marks the line optional. Wording is advice ('could stand in'), never a guarantee.

## SHOP-6 — Shopping list: metric and US amounts add up, shown in US amounts by default

Closes SHOP-OPEN-1 by the owner's ruling. Today 200 g + 8 oz stays two parts on one line because only exact ladders are summed (src/data/shoppingList.js, merge-rule header). New rule: a weight adds to a weight and a volume adds to a volume across metric and US (1 oz = 28.3495 g, 1 lb = 16 oz; US cup 236.588 ml, tbsp 14.787 ml, tsp 4.929 ml, fl oz 29.574 ml; cl and l as today). Weight is still never turned into volume or the reverse, count words (cloves, sprigs, dashes) are untouched, and unlike kinds still show as two parts. What is STORED must stay exactly what was entered (no rounding written back, so Undo, sync and the other display stay exact); the total is worked out for display. Display system: US by default (oz and lb; tsp, tbsp, cups; fl oz for drinks, written the way a US cook reads them, with the fractions 1/4 1/3 1/2 2/3 3/4 and no false precision such as 7.05 oz), with one switch on the list, 'US | Metric', remembered on the device (say where it is kept and whether it syncs; default: device only). Metric display rounds to sensible steps (5 g, 5 ml, or 1 for small amounts). The word 'about' is shown only when the number on screen is not exact (a conversion between systems happened, or rounding changed it); a line entered and shown in the same system reads exactly as before. Copy list and the add summary ('garlic: now 5 cloves') use the same display. Do not change how recipe cards elsewhere in the app print their own amounts; name that as out of scope in the report. Update docs/shopping-list.md (the merge table and a short 'US and metric' section with the factors and rounding steps) and move SHOP-OPEN-1 in BACKLOG.md to decided, with the owner's words.
