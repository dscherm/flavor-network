# weak as-built specs

## WEAK-A — Everyday-pairs index for the invent and kitchen features

pairings.json is missing the most common pairs in cooking (chicken|garlic, garlic|onion, garlic|olive oil, beef|onion …). 07-blend-v2.js weights NPMI, on which hub pairs score low, and keeps only the strongest 40k. Option A (owner-approved): a separate index built from the raw RecipeNLG counts, used only by the invent and kitchen features. scripts/build_everyday_pairs.mjs (rule in src/data/everydayPairsSelect.js) maps co-occurrence names onto the app vocabulary: 3,353 exact plus 136 through spelling variants and aliases, with counts summed. It drops TRIVIAL + SUGGESTION_EXCLUDE and keeps pairs with count >= 30 and PMI > 0. It scores each pair log10(count)^3 * cbrt(min(PMI,3)), keeps each ingredient's top 32 (either side) and quantile-maps the score percentile onto the curated tradition strengths. Output: public/proDataset/everyday_pairs.json, 488 KB, 35,701 pairs, 2,906 names, deterministic. src/data/everydayPairs.js has a cached, fail-safe loader (null on failure), strength(), partners() and blendIndex(curated, everyday): the buildPairingIndex shape with the per-pair max. It is wired into Invent a recipe (InventRecipe.jsx) and the Sauce Lab pantry context (Invent a sauce + My pantry stand-ins) through useEverydayPairs. The cocktail lab is not wired: links rose from 73% to 82%, but the top picks got worse (Margarita → rum sour), and its single index also drives Riff. pairings.json/.bin, the Pairing Lab, the Cookbook 'goes well with' ranking and evalPairingMatch are untouched. Before/after in docs/everyday-pairs.md (scripts/measureEverydayPairs.mjs, real set-completion model via onnxruntime-node).

## WEAK-4 — Amount model: kitchen units and kitchen fractions (no more '3.6 each')

The FM-Q2 amount model (public/models/quantity_model.json) that prefills amounts in the Recipe Notebook, Invent a recipe and the kitchen hand-offs gave unusable amounts ('chicken: each 3.6', 'pasta: each 4.54', 'c 0.83' vs 'cup'). Root cause is in FM-Q1's line parser (fm_p0_2_build_corpus.mjs parseLeadingAmount): a unit counted only when the lowercased token was literally a UNIT_DENSITY key, so plurals (cups, lbs, ounces, tablespoons, teaspoons), parenthetical packages ('1 (16 oz.) pkg.'), unsized cans/packages and 'garlic cloves' all became 'each' = 100 g, and 'T.' (tablespoon) became 't' (teaspoon). On the first 100k recipes 27% of quantity lines were 'each' and only 42% of those were real counts. FM-Q2 then took the modal raw unit and qty = median grams / density, so 'each 4.54' was 454 g. Fix at the source: src/ml/ingredientLineParser.js re-parses RecipeNLG lines (package sizes converted to weight, plural/abbreviated units, case-sensitive T/t, ranges, unicode fractions, count nouns, stick butter, plausibility caps); flavor-gnn/scripts/weak4_quantity_model.mjs re-parses once (12.08M triples), picks volume / weight / count per ingredient by vote with the ingredients.json category default as tie-break (runner-up within 80%), takes the median amount in that dimension and expresses it via src/ml/kitchenUnits.js category rules (spices tsp; oils and sauces tbsp below 1/4 cup; meat, fish and pasta by the pound from ~1/2 lb; small weights in oz; counts keep their noun: each / clove / can / pkg) rounded to kitchen fractions (spoons 1/8 1/4 1/2 3/4, cups 1/4 1/3 1/2 2/3 3/4, quarter pounds, whole cloves, half steps for 'each' below 2). quantityModel.predictQuantity adds a post-processing layer (kitchenize: normalise unit names, round) so any older artifact also yields kitchen amounts; quantityRuntime writes raw as ASCII kitchen fractions ('1 1/2 lb') that parseAmount re-reads. portionParser gains 'can' (425 g) and 'pkg' (250 g). API unchanged ({unit, qty, source} / {raw, qty, unit, inferred}); artifact 186 -> 212 KB.
